# REA V0.3 — First AI Team

## Goal

V0.3 introduces the first multi-agent engineering team while preserving the V0.1/V0.2
governance boundary. The team can reason about a GitHub Issue and repository knowledge, but it
cannot mutate source code, push branches, merge PRs, deploy, or make cost-bearing decisions.

## Team

The first team has four independent roles:

1. **Engineering Manager** — translates business intent into an engineering brief.
2. **Tech Lead** — validates architecture and risk, rejects invalid approaches, and decomposes work.
3. **Senior Developer** — proposes file-level implementation steps, tests, assumptions and commands.
4. **Code Reviewer** — independently reviews the work package and may approve or request changes.

Roles route through capabilities in `config/models.yaml`; they are not permanently bound to a model.

## Planning flow

```text
GitHub Issue
     |
     v
Knowledge Context Builder
     |
     v
Engineering Manager
     |
     v
Cost Gate
     |
     v
Tech Lead
     |
     +---- reject ----> stop
     |
     v
Cost Gate
     |
     v
Senior Developer
     |
     v
Command Policy Classification
     |
     v
Work Package JSON
```

The Senior Developer does not execute the commands it proposes. Every proposed command is parsed
and classified by the deterministic command policy as `allow`, `ask`, `deny` or `cost_approval`.

## Review flow

```text
Work Package JSON
       |
       v
Knowledge Context Builder
       |
       v
Independent Code Reviewer
       |
       +---- approve
       |
       +---- request_changes
       |
       v
Review JSON
```

V0.3 review is plan-level. Source-code diff review begins when V0.4 is allowed to create changes.

## CLI

Before planning work, scan the target repository:

```bash
rea repo scan ../social-media
```

Then create a work package from a GitHub Issue:

```bash
rea team plan 123 --repo tbarletta/social-media
```

The GitHub repository basename is used as the default knowledge repository. If catalog entries are
ambiguous, specify the exact inventory:

```bash
rea team plan 123 \
  --repo tbarletta/social-media \
  --knowledge-repo social-media \
  --knowledge-root /workspace/social-media
```

Review the generated package:

```bash
rea team review .rea/work/issue-123-plan.json
```

Exit codes:

- `0` — plan/review completed and review approved
- `10` — reviewer requested changes
- `20` — human cost approval required
- `30` — Tech Lead rejected the request

## Knowledge precedence

The prompt context explicitly carries the project knowledge hierarchy:

1. explicit human-approved decision
2. approved ADR
3. documented business rule
4. production code
5. documentation
6. Git history
7. AI inference

Facts are sorted so `confirmed` and `documented` evidence reaches the model before inferred
knowledge. Inference is never promoted to a permanent decision by V0.3.

## Cost governance

Every agent output contains a `cost_impact` field. The workflow stops immediately when any stage
sets it to true and records a `team.cost_gate` audit event. A later release may resume an approved
work unit after explicit human approval; V0.3 intentionally does not implement automatic resume.

## Audit events

V0.3 adds:

- `team.context.loaded`
- `team.handoff`
- `team.cost_gate`
- `team.blocked`
- `team.command.proposed`
- `team.plan.saved`
- `team.review.saved`

The existing audit redaction rules continue to apply.

## Security boundary

V0.3 deliberately does **not**:

- edit repository files
- create branches
- execute developer-proposed commands
- push commits
- create or merge PRs
- write to production
- bypass the command policy
- approve cost-bearing changes

Those capabilities belong to the governed Level 6 implementation in V0.4.
