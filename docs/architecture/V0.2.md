# REA V0.2 — Knowledge Engine

## Goal

Turn an unknown repository into an auditable engineering inventory without relying on an LLM for facts that can be discovered deterministically.

## Pipeline

```text
Repository
  -> bounded file inventory
  -> language detection
  -> manifest discovery
  -> framework/data/messaging/infra/test/API analyzers
  -> AST/import providers
  -> governed Git history
  -> dependency graph
  -> JSON knowledge store + multi-repository catalog
```

## Evidence and confidence

Every knowledge fact carries evidence and one confidence level:

- `confirmed`: deterministic evidence in source, manifest or config
- `documented`: reserved for explicitly documented knowledge
- `inferred_high`
- `inferred_medium`
- `inferred_low`

LLM-generated architecture or business knowledge must never be persisted as `confirmed` unless promoted by deterministic evidence or human approval.

## Scanner safety

- `.git`, dependency caches and build outputs are excluded from file traversal.
- Text reads are bounded by a per-file byte limit.
- Repository scans have a maximum file count.
- Git history is collected through `GovernedLocalRunner`.
- The runner calls the central `CommandPolicy` before every subprocess invocation.
- `ASK`, `DENY` and `COST_APPROVAL` decisions are never executed by the scanner.

## Analyzer architecture

`RepositoryAnalyzer` is the extension contract for deterministic analyzers. V0.2 includes:

- ManifestAnalyzer
- FrameworkAnalyzer
- DataAnalyzer
- MessagingAnalyzer
- InfrastructureAnalyzer
- TestAnalyzer
- ApiAnalyzer

`AstProvider` is the source-structure extension contract. V0.2 includes:

- PythonAstProvider using the Python standard library AST
- TypeScriptImportProvider for deterministic JS/TS import edges
- TreeSitterProvider extension point for future configured grammars

## Multi-repository catalog

`JsonKnowledgeStore` writes one immutable-style inventory snapshot per repository identity and updates a local `catalog.json` with summary metadata. Repository identity includes both name and root path, avoiding collisions for equal repository names in different workspaces.

The next persistence step is PostgreSQL. `infra/postgres/001_knowledge.sql` prepares tables for repositories, facts and dependency edges plus a nullable pgvector embedding field. Embedding dimensionality remains intentionally unconstrained until the embedding model is selected.

## Git history

The scanner samples recent commits using only allowlisted read operations:

```text
git branch --show-current
git log ...
```

Git history is supporting evidence, below production code and documentation in the REA source-of-truth hierarchy.

## V0.2 boundaries

V0.2 does not yet:

- infer business rules using an LLM
- persist embeddings
- run semantic RAG
- build a global cross-repository symbol resolver
- modify repositories

Those capabilities build on this deterministic inventory rather than replacing it.
