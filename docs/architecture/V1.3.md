# REA V1.3 — Endurecimento arquitetural

A V1.3 fecha os principais caminhos de escape identificados na revisão arquitetural da V1.2.

## Fronteiras corrigidas

- Benchmarks de baseline e candidato executam em Docker sem rede, capabilities ou ambiente do host.
- Validações Level 6 são seguidas por uma verificação completa dos arquivos alterados.
- Qualquer modificação fora do plano aprovado aborta o experimento antes do stage e commit.
- O sandbox possui limites de CPU, memória, PIDs, tempo e filesystem temporário.
- Métricas de segurança ausentes são desconhecidas e bloqueiam promoção.
- Promoção exige branch protection forte e checks obrigatórios pelo nome.
- Comandos de deployment passam pelo mesmo runner governado e auditado.
- Ações Git da conversa deixaram de usar uma execução paralela à política central.

## Skills

- eventos de auditoria possuem IDs persistentes;
- a CLI conecta o ciclo de skills ao audit log;
- testes funcionais são obrigatórios;
- a identidade gerada deve corresponder à proposta;
- versões precisam avançar em SemVer;
- conflitos concorrentes no registro são detectados;
- dependências são reavaliadas;
- versões em quarentena ou rollback podem gerar uma revisão;
- o gerador não recebe tokens e credenciais do ambiente;
- existe daemon contínuo;
- skills ativas podem ser invocadas pela conversa com `/skill ID {JSON}`.

## Imagem de benchmark

Antes de executar a autoevolução:

```bash
docker build \
  -f infra/benchmark/Dockerfile \
  -t rea-benchmark:1.3.0 .
```

A imagem deve ser construída e controlada pelo operador. O benchmark falha de forma segura quando
a imagem não existe.

## Controles externos ainda obrigatórios

O código não consegue ligar fisicamente um runner offline nem contratar funcionalidades do GitHub.
A operação autônoma continua exigindo runner disponível, proteção da `main`, checks obrigatórios
e credenciais de privilégio mínimo.
