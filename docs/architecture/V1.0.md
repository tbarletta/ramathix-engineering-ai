# REA V1.0 — AI Engineering Organization

V1.0 evolves Ramathix Engineering AI from a governed Level 6 engineering team into an
engineering organization that can translate strategic goals into an ordered, auditable work
portfolio.

## Operating model

```text
User strategic goal
        |
        v
AI Engineering Manager
        |
        +--> Initiatives
        |       |
        |       +--> Projects
        |               |
        |               +--> Work Units
        |
        v
Deterministic Portfolio Planner
        |
        +--> dependency validation
        +--> priority score
        +--> topological ordering
        |
        v
V0.7 deterministic risk preflight
        |
        +--> READY
        +--> GOVERNANCE_APPROVAL_REQUIRED
        +--> COST_APPROVAL_REQUIRED
        +--> BLOCKED
        |
        v
Explicit GitHub Issue publication approval
        |
        v
GitHub Issue
        |
        v
rea issue run
        |
        v
Full V0.7 specialist governance
Security + Performance + Cloud + FinOps
        |
        v
Specialized Level 6 Issue-to-PR
```

## Why governance is two-stage

Portfolio planning may produce many candidate Work Units. Running every specialist model against
every candidate before the work exists would be unnecessarily expensive in latency and local GPU
usage. V1.0 therefore performs a deterministic V0.7 Risk Engine preflight during portfolio
planning, and the existing complete V0.7 specialist review immediately before Level 6 execution.

This does not weaken execution governance: no Work Unit reaches autonomous code execution without
the full V0.7 gate.

## Portfolio priority

The Engineering Manager proposes normalized inputs from 1 to 5. The final score is code-owned:

```text
priority = business_value * 5
         + strategic_fit * 4
         + urgency * 3
         - effort * 2
```

Dependency depth is applied before score ordering. A dependent Work Unit can never be placed ahead
of its prerequisites merely because the model gave it a higher business score.

## Approval boundaries

The following approvals are independent:

- `github-issue-create`: authorizes creation of GitHub Issues from an organization plan.
- `--approve-tech-lead WU-...`: authorizes a HIGH-risk Work Unit.
- `--approve-human WU-...`: authorizes a CRITICAL-risk Work Unit.
- `--approve-cost WU-...`: explicit human approval for a Work Unit with potential monetary cost.

A Work Unit that is both HIGH risk and cost-impacting requires both cost approval and risk approval.
A production-write Work Unit remains blocked regardless of supplied flags.

## CLI

Create a portfolio:

```bash
rea org plan \
  "Reduce content production lead time by 40%" \
  --repo tbarletta/social-media \
  --repo tbarletta/media-engine \
  --constraint "Do not add paid providers"
```

Inspect plans:

```bash
rea org list
rea org show org-20260821-ab12cd34
```

Publish eligible Work Units:

```bash
rea org publish org-20260821-ab12cd34 \
  --approve-rule github-issue-create
```

Publish a high-risk unit after explicit Tech Lead approval:

```bash
rea org publish org-20260821-ab12cd34 \
  --unit WU-004 \
  --approve-rule github-issue-create \
  --approve-tech-lead WU-004
```

A cost-impacting high-risk unit additionally requires:

```bash
--approve-cost WU-004
```

## Persistence

Organization plans are stored under:

```text
.rea/organization/<plan-id>.json
```

The plan records initiatives, projects, Work Units, priority, dependencies, governance preflight,
publication state and created GitHub Issue references.

Publication state is saved after each Issue creation, so a later failure does not discard already
published work.

## Safety invariants

1. The Engineering Manager cannot publish Issues without the explicit GitHub write approval.
2. Repository names in generated Projects and Work Units must be from the user-supplied repository
   allowlist.
3. A Work Unit must stay in the repository assigned to its Project.
4. Dependency cycles are rejected deterministically.
5. Production writes remain blocked.
6. Cost approval is per Work Unit and cannot be inferred from general governance approval.
7. HIGH and CRITICAL risk approvals remain independent from cost approval.
8. Merge and deployment remain outside organization autonomy.
9. Every published Work Unit is governed again by the full V0.7 specialist gate before Level 6.
